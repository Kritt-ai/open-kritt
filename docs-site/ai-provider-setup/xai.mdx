title: "xAI"

The **xAI** provider uses `XAI_API_KEY` to call Grok models through xAI's API. open·kritt
defaults this provider to the **Grok Build** harness (`grok-build`, alias `grok`).

After the key is configured, the engine periodically refreshes a searchable model catalog
from xAI's authenticated models endpoint. The results reflect the models returned for that
key and are cached for the create-scan and AI-generation forms. The catalog is advisory:
you can also enter an exact model ID as a custom value, like OpenRouter.

## Create and configure the key

<Steps>
  <Step title="Create an xAI account">
    Sign in to the [xAI Console](https://console.x.ai/) and open billing or credits if your
    workspace requires prepaid usage for API access.
  </Step>
  <Step title="Create an API key">
    In the console, create an API key and copy it when shown. Store it securely; xAI does
    not show the full secret again.
  </Step>
  <Step title="Save it in open·kritt">
    Run `./kritt setup`, choose **xAI API key**, and paste the key into the hidden input.
    The CLI writes it to `XAI_API_KEY` in `.env`. You can also add or replace the key from
    the running application's **Accounts** page; Accounts keeps the key synchronized with
    `.env` and the engine credential store.
  </Step>
  <Step title="Start or recreate the stack">
    ```bash
    ./kritt start
    ```

    Stop an already-running attached stack with Ctrl+C first.
  </Step>
  <Step title="Choose a model">
    Search the xAI model picker in the scan or generation form. open·kritt defaults to
    `grok-4.5`. If the model you need is not listed, enter its exact xAI model identifier
    as a custom value.
  </Step>
</Steps>

## Harness and model compatibility

xAI supports only the **Grok Build** harness. The engine image pins the Grok Build CLI to
**1.0.0** (`/usr/local/bin/grok`).

Whether selected from the catalog or entered manually, the model must support the agent
behavior needed by Grok Build, including a large code context, tool use for scans, and
reliable structured output.

**Thinking effort** is supported at `low`, `medium` (the open·kritt default), and `high`.
The UI shows only levels supported for the selected model and harness.

## Catalog refresh and fallback

The engine refreshes the xAI catalog in the background and stores only the sanitized model
metadata needed by the UI. While the first refresh is still running, the forms may show the
catalog as loading. A successful refresh replaces the cached choices.

If a later refresh fails, open·kritt keeps the last usable cached catalog. If no successful
catalog has been cached yet, model discovery is shown as unavailable; check the engine logs
and the configured key, then retry. You can still use an exact custom model ID as the
compatibility escape hatch.

## Verify and troubleshoot

- `./kritt setup` should show **xAI API key present**.
- The create and generation forms should list **xAI** and load a searchable model catalog.
  An exact custom ID can also be entered when needed.
- If the catalog remains in a loading or unavailable state, inspect
  `docker compose logs engine` and confirm the configured key can list models.
- A `401` usually means the key is invalid or revoked. Billing or quota errors generally
  mean the account cannot run the selected model.
- A model-not-found error usually means the identifier is misspelled or unavailable to the
  account. Copy the exact ID from the model catalog or xAI documentation.
- If a run starts but cannot use tools or return valid structured output, choose a model
  with the required capabilities or review Grok Build logs in the scan attempt output.

See xAI's official [API documentation](https://docs.x.ai/) for current model availability
and billing behavior.
